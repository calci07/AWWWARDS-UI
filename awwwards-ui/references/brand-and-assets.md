# Brand and generated assets

Use this reference only after the user approves a route. Stage A may inventory needs and present prompt directions, but it must not generate assets or mutate the codebase.

## Capability preflight

1. Inspect authentic brand, product, photography, packaging, interface, legal, and rights materials.
2. Re-read the current `design-taste-frontend` skill and apply only relevant rules.
3. Read `brandkit` when discoverable. Otherwise disclose the gap and use this bundled brand-system contract.
4. Read `imagegen-frontend-web` for approved web image direction.
5. Read `imagegen-frontend-mobile` when discoverable. Otherwise disclose the gap and use `mobile-app-web.md`.
6. Use the system image-generation capability/GPT Image 2 for approved bitmap assets when available. Never claim an unavailable skill, model, or tool ran.

Generated imagery cannot replace authentic evidence, identity, customers, facilities, outcomes, awards, product claims, or documentary events.

## Brand-system contract

Create a project-native, documented system containing:

- premise, audience promise, attributes, and verbal tone;
- supplied marks and usage constraints, without redrawing an owned logo;
- primitive and semantic color tokens with contrast notes;
- display, text, data, and utility typography roles using available fonts;
- photography, illustration, icon, material, texture, crop, and motion languages;
- representative use across hero, product, editorial, mobile, and functional UI;
- provisional decisions, rights limits, and content still awaiting approval.

Integrate approved foundations into the repository's existing token, theme, component, and asset conventions. Do not introduce a parallel design system when a suitable one already exists.

## Continuity bible and asset ledger

Before the first generation, lock a continuity bible: palette, light direction, camera/lens or rendering viewpoint, perspective, material vocabulary, texture scale, grade, retouch, controlled imperfection, crop grammar, negative space, and five to ten relevant exclusions.

Record every asset:

| Field | Required record |
|---|---|
| ID and role | Page/section/component, narrative job, meaningful or decorative |
| Truth source | Supplied reference, verified detail, or declared concept |
| Family | Campaign, product, background, texture, illustration, icon, or effect pair |
| Formats | Wide, portrait, phone, detail, transparent, copy-safe zones |
| Relationship | Independent master, master edit, or approved crop |
| Direction | Prompt, exclusions, palette, light, viewpoint, material, grade |
| Integration | `transparent-object`, `matched-field`, `container-crop`, or `full-bleed`; background owner/token; alpha/opaque master; safe zones; overscan; intended cutoff edges; shadow behavior |
| Governance | Rights, consent, disclosure, owner, status, rejection reason |
| Placement | Repository path, consuming component/page, crop and alt intent |

Variation may change subject or scale, not the visual world.

## Asset classes

- **Product mockups:** preserve supplied geometry, labels, marks, colors, ports, materials, and proportions. Generate environments around product truth; never invent it. Standalone mockups default to a true-alpha master unless an approved contextual scene requires an opaque plate.
- **Campaign/editorial imagery:** direct a specific human or material story, plausible production conditions, purposeful copy space, and separate mobile compositions where needed.
- **Backgrounds/textures/elements:** support hierarchy; test seams, alpha, compression, responsive crop, and text contrast.
- **Expressive illustrations and icons:** one governed family with defined stroke, fill, perspective, corner, texture, and metaphor rules. These may be generated.
- **Functional icons:** coherent, editable SVG or code-icon components from an authorized source. Do not use generated raster icons.
- **Device scenes:** keep product UI as real editable markup when possible; do not bake unreadable or invented UI into images.

## Master-and-edit workflow

Approve one master before dependent variants. For plain-to-metal or other paired reveals, lock canvas, camera, crop, silhouette, landmarks, background, light direction, and shadow; edit only the named material. Verify registration with an opacity flicker or difference overlay. Create a separate mobile master when composition changes, then derive the mobile pair from it.

Prompt independent masters with observable production choices: subject/action; verified details; environment/materials; editorial role; light; camera/viewpoint; crop/copy-safe zone/aspect ratio; palette/grade; controlled imperfections; placement; exclusions. Prompt dependent edits to preserve named invariants and change one property only. Do not imitate a living artist's identifiable style.

## Repository placement

Use existing asset directories, naming, import, optimization, and licensing conventions. Choose formats by use: SVG for functional vectors; AVIF/WebP or repository-native responsive formats for photography; PNG only when alpha or lossless behavior requires it. Preserve masters outside destructive build pipelines, and wire responsive sizes, dimensions, lazy/eager policy, and alt/decorative treatment in code.

## Anti-synthetic review

Reject any result with identity, anatomy, text, geometry, perspective, contact, reflection, gravity, or shadow failures; fake logos or evidence; generic luxury staging; plastic retouching; random bloom/haze; family drift; failed copy-safe zones; mismatched paired registration; unresolved rights; or quality that survives only when blurred or tiny. Regenerate or re-edit instead of concealing defects.
